# App architecture

This document explains what goes where in Haku and why, where the reason is not obvious from the code.

## What Haku is

A lightweight desktop browser built on Tauri v2. Its distinguishing idea is that tabs and webviews are not the same thing: a small, configurable pool of real webviews is shared between any number of tabs, so memory stays close to flat as tabs accumulate.

## The one big decision

**Rust owns the browser. The interface renders it.**

`browser::Browser` holds every tab, its navigation history, and the webview pool, and it is the only thing allowed to change them. The React application in the chrome webview keeps no tab state of its own: it sends intents (`open_tab`, `select_tab`, `navigate_tab`) and renders the `StateChanged` events that come back.

This was chosen over a TypeScript-side model because several windows were planned from the start, and Haku now has them: a model living inside one window cannot be the authority for the others. Moving it once a second window existed would have meant rewriting every feature built on top of it.

## Layout

```
haku/
├─ src/                       React interface (the "chrome" webview)
│  ├─ bindings.ts             GENERATED by `pnpm bindings` — never edit
│  ├─ app/                    shell, internal-page routing, theme
│  ├─ ipc/                    typed wrappers, external store, hooks
│  ├─ features/               tabs, toolbar, viewport, overlays, feedback, settings, history, context-menu, extensions, memory, popup, window-controls
│  ├─ shared/                 i18n, utilities
│  └─ styles/
└─ tauri/src/
   ├─ browser.rs              the authority; no Tauri types
   ├─ browser_tests.rs        its tests, included with #[path]
   ├─ model/                  tab, history, pool, window, page state, dialog, context menu,
   │                          extension, keymap, optimization, pressure, preview
   ├─ webview/                applies Effects to real webviews; scripts injected into pages
   ├─ chrome/                 viewport + overlay geometry → native input mask
   ├─ platform/               native operations Tauri does not expose: layering, page observation,
   │                          dialogs, context menus, popups, key and failure handling, extensions,
   │                          freezing, idle workers, memory measurement (Windows only)
   ├─ storage/                settings + session (JSON), history (SQLite)
   ├─ ipc/                    commands, events, binding export
   ├─ error.rs · state.rs · lib.rs
```

## Layers

```
React interface  →  generated bindings  →  Tauri commands  →  Browser  →  Effects  →  real webviews
      ↑                                                                                    │
      └──────────────────────── StateChanged events ───────────────────────────────────────┘
```

### `browser.rs` — the authority

`Browser` contains no Tauri types at all. It decides what _should_ be true and returns a `Vec<Effect>` describing the difference: create this webview, park that one on `about:blank`, show this, hide that.

That separation is what makes tab and pool behaviour testable without a window, a webview, or an event loop. Every rule about eviction, pinning, discarding and history is exercised by ordinary unit tests.

Each populated window stores disjoint adjacent tab pairs with individual ratios. Selecting a tab projects its pair or the tab alone into an ordered viewport assignment list with a focused viewport; `active` is derived from that assignment. [Split view slice 4b](specs/split-view.md#implementation-slices) permits several background pairs and at most two on-screen viewports in normal windows; popups keep one. The strip joins pair members and moves them as a unit; header-free panes show a focused outline, with waiting-dialog badges on tabs. The interface renders assignments with per-pane covers and internal-page boundaries; the shared toolbar and window-modal dialogs follow the focused tab. Visibility, pool protection and optimization follow assignments, not focus, and geometry is revisioned separately from session state.

Every mutation ends by calling `realize()`, which reconciles the whole state, rather than emitting effects itself. There is therefore exactly one description of what "correct" looks like, and no operation can forget a step another one remembers.

### `model/` — the pieces

`tab.rs`, `history.rs` and `pool.rs` hold the data and the rules that belong to it alone. A tab's back/forward stack keeps at most 50 entries, as many as the engine's own, dropping the oldest: every `StateChanged` carries each tab's whole stack, and a page that pushes a route on every scroll or keystroke would otherwise grow it without end. Sending only the current entry was rejected because a back button's list of earlier pages would then need a command of its own. `WebviewPool` is deliberately ignorant of tabs beyond their identity: the caller decides which tabs may not be displaced and what the effective capacity is, which keeps the eviction policy independently testable.

### `webview/` — the Tauri side

Applies `Effect`s to real webviews. It knows how to drive a webview, not what to do with one. It attaches `platform::observe_page` to every content webview and hands what it reports — URL changes, titles, native back and forward, dialogs — back to the caller through a `PageObserver`, so this module never touches application state. See [Page observation](specs/page-observation.md).

### `chrome/` and `platform/` — layering the interface over the page

See [Chrome layering](specs/chrome-layering.md). `chrome/` converts the geometry the interface reports into physical rectangles; `platform/` performs the native operations Tauri does not expose.

### `storage/` — what survives a restart

Settings and the open-tab session are small, read whole, and worth being able to hand-edit, so they are JSON. History grows without bound and will need ranged and filtered queries, so it is SQLite. Both are read through `read_json`, which layers a stored document over the type's defaults, so a file naming one key does not reset the rest.

### `ipc/` — the boundary

`ipc::builder()` is the single description of the command and event surface. The running application and the TypeScript binding generator both read it, so the bindings cannot describe a command Rust does not have. `src/bindings.ts` is generated by `pnpm bindings` and is never edited by hand.

## Frontend

```
src/
├─ bindings.ts        generated; do not edit
├─ app/               shell, routing for internal pages, theme
├─ ipc/               typed wrappers, the external store, React hooks
├─ features/          one folder per feature: tabs, toolbar, viewport, overlays, feedback, settings, history, context-menu, extensions, memory, popup, window-controls
├─ shared/            i18n, utilities
└─ styles/            imports, Haku's surface tokens, density
```

State reaches React through `useSyncExternalStore` over the Rust event stream. There is no client-side cache to invalidate and nothing to keep in sync.

Commands are called through `@ipc/commands`, a wrapper over the generated bindings that passes every failure to one handler. `features/feedback` points that handler at a toast, and owns the one `@codenhub/toaster` instance that every notification and page dialog goes through.

### Styling

Components from `@codenhub/styles` are used wherever one fits — buttons, fields, cards — in its default monochrome palette. Pieces with no component, such as tabs and the address field, are Tailwind utilities over the same tokens, plus Haku's two surface tokens (`chrome`, `chrome-raised`). Density is an attribute on the shell; compact is the default and applies to the bars only.

The bars follow Helium's proportions: 28px controls with the package's 8px control radius — rounded, not pill-shaped — 3px between the tab row, the toolbar and the page, and a 4px margin around the page.

## Internal pages

Pages Haku renders itself — new tab, settings, history — use the `haku://` scheme and are drawn by the chrome, not loaded into a webview. A tab on one of them therefore consumes no pool slot, shares the interface's theme and translations, and can talk to Rust directly.

The host names the page; a path, query or fragment after it belongs to the page, so `haku://history?q=…` reaches the history page.

## Where this is heading

[First release](first-release.md) records the decisions the next features are built on. Several windows sharing one pool, native keyboard handling while a page has focus, paired panes, split session restoration and private windows with labelled browser and popup chrome are built; named containers still wait for Tauri profile-name support. Read it before building anything it lists.

## Threading

Commands that drive a webview are `async`. Tauri runs synchronous commands **on the main thread**, and creating, moving or raising a webview dispatches work to that same thread and waits for it — which deadlocks the event loop. Commands that only read state stay synchronous.

This is not a theoretical concern: it was the cause of a silent failure where webviews were created but never navigated, because the event loop was blocked inside webview creation.

Changes to the browser that produce effects go **one at a time**, from deciding them to applying their effects, through `Changes` in `state.rs`. Effects name slots, not tabs, so a batch applied after a later one can undo it: a periodic tick that discards a tab, applied after a select that reused its slot, blanks the selected page. The browser's own lock is still released before webviews are touched, so reads never wait on a native call. Nothing on the main thread may start one, since applying waits on that thread. Page reports that produce no effects, such as a navigation starting, a page loading or a window gaining focus, write the browser directly under its own lock on the main thread: with nothing to apply, they cannot be applied out of order.

## Security

Content webviews load arbitrary remote pages, so they are given nothing:

- The Tauri capability is scoped to `webviews: ["window-*"]`, the label each window's chrome shares with its window. Chrome webviews alone receive core permissions; content webviews are labelled `content-N`, which the pattern never matches. It must not name `windows`: a window scope also covers every child webview in the window, content webviews included.
- No capability grants remote origins IPC access, so a page has no channel into the application at all.
- Every command guards with `ensure_chrome`, rejecting any caller that is not a window's interface, and acts for the window that called it.
- Page metadata is observed from Rust rather than reported by the page. Rust evaluates an expression in the page to read what an injected script recorded; the page has no way to call back. See [Page observation](specs/page-observation.md).
- Dialogs a page opens are drawn by the chrome, titled with the requesting site, so a page cannot present its text as Haku's.
- The chrome, the one webview with IPC, runs under a content security policy (`app.security.csp` in `tauri/tauri.conf.json`): scripts and styles only from the bundle, no plugins, frames, form posts or `<base>`, and network access only to Tauri's IPC. Images may come from any `http`, `https` or `data:` source, because tab favicons are the sites' own. Tauri adds a hash and a nonce for the bundle's own scripts and styles when it serves them. Styles set through the CSSOM, as React's `style` props and the toaster's rules are, are not subject to the policy. Tauri sets the policy only on what it serves from the bundle, so `pnpm tauri dev`, which loads the interface from Vite's dev server, runs without one; check a change to the policy in a built app (`pnpm tauri build --debug --no-bundle`).

## Dependencies

Runtime dependencies are of two kinds. The platform packages are React (`react`, `react-dom`) and Tauri's JavaScript API (`@tauri-apps/api`). Four first-party packages come from `@codenhub`: `@codenhub/theme` (preference storage and the pre-paint script), `@codenhub/styles` (tokens, palette, reset and components, through its Tailwind source entry), `@codenhub/icons` and `@codenhub/toaster` (notifications and dialogs).

Apart from those, Haku builds its own code. General-purpose libraries with breaking changes pending are a poor foundation for a project meant to avoid repeated refactors. Do not add a runtime dependency unless simple in-house code is clearly worse. Development tooling — formatters, linters, test runners — is not covered by this rule, since none of it ships in the app.

## Platforms

Windows is implemented. On macOS and Linux every native operation in `platform/` resolves to `platform/unsupported.rs`, which returns `HakuError::Unsupported` rather than silently doing nothing. The interface is shared, so adding a platform means filling in a known interface, not redesigning. CI verifies Rust on Windows only, for that reason ([CI](ci.md)).
