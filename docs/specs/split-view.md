# Split view

This spec builds on [First release § Viewports, not a viewport](../first-release.md#viewports-not-a-viewport). The [decisions](#decisions) below govern implementation. Rust remains the authority; React renders browser state and reports measured geometry.

## Problem

Before split view, Haku equated the selected tab with the only page visible in each window. Comparing two pages required switching tabs or opening another window. Adding a second content element alone would have left its page hidden, unprotected, incorrectly positioned, or targeted by commands for the other page.

## Model

Each normal window has an ordered list of one or two viewports, each with a stable window-local id and exactly one tab belonging to that window. A tab appears in at most one viewport. Removing a pane does not renumber the survivor. Popups retain exactly one viewport and cannot split.

**Visible tabs** are the assignments, including internal and crashed tabs. **Focused viewport** is the last pane chosen for browser actions, even while the address field or a menu has native focus. Its assignment is the **focused tab**. Native webview focus and window focus are separate facts. Losing window focus does not clear pane focus or visibility. `active` remains a derived compatibility projection of the focused tab, never an independently mutable id; the toolbar, address field and existing selected-tab appearance follow it.

| Action                                                    | Result                                                                                                                                                                                                                                                                                                                                        |
| --------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Select a hidden tab                                       | Replace the focused pane's assignment; the old tab becomes background.                                                                                                                                                                                                                                                                        |
| Select a tab already visible                              | Focus its existing pane; do not swap, duplicate or reload it.                                                                                                                                                                                                                                                                                 |
| Open a foreground tab from chrome, or reopen a closed tab | Use selection rules in the destination window's focused pane. Reopening restores the tab, not its former split.                                                                                                                                                                                                                               |
| Open a foreground tab from a page                         | Replace the source page's pane and focus it. Preserve opener connection and insertion order under [Windows and popups](new-windows.md). Background opens leave assignments alone.                                                                                                                                                             |
| Close a visible tab                                       | Prefer its same-window opener, then the tab to its right, then scan left, excluding tabs already in other panes. Assign the first available candidate to that pane. If only already-visible tabs remain, remove the empty pane and focus the survivor. If the opener is already visible, remove the closing pane and focus the opener's pane. |
| Close a hidden tab                                        | Keep assignments and pane focus.                                                                                                                                                                                                                                                                                                              |
| Close a pane                                              | Remove its assignment, keep its tab open in the strip, expand and focus the survivor. Its former tab is subject to ordinary background policy.                                                                                                                                                                                                |

Closing an unfocused pane's tab preserves focus unless that pane disappears and the opener rule above applies. Closing the window's last tab retains the existing home-page replacement. Closing a popup's tab still closes its window. Tab order is independent of pane order. Ctrl+Tab and positional shortcuts keep strip order and apply the same selection rules, including focusing an already-visible tab.

## Layout and IPC

Rust owns pane ids, assignments, focused id and committed ratio. React owns measurement and temporary divider-drag geometry. Ratio is the first pane's share of the available width after the divider; orientation is side by side only. Geometry is never session state.

Additions to each window's `BrowserState` (existing fields remain):

```ts
viewports: {
  id: string;
  tab: TabId;
}
[];
focusedViewport: string;
splitRatio: number | null; // null for one pane
layoutRevision: number; // changes with the set of panes or committed ratio
// active is derived from focusedViewport
```

Replacement for `Layout`, still passed as the `layout` argument of async `set_layout`:

```ts
type Layout = {
  revision: number; // BrowserState.layoutRevision being rendered
  viewports: {
    id: string;
    rect: Viewport; // existing x, y, width, height, in chrome CSS pixels
    covered: boolean; // internal page, crash notice or restoring preview
    radius: number; // measured from this pane's CSS
  }[];
  overlays: Overlay[]; // existing window-relative rectangles and radii
};
```

Every assigned pane is reported, including covered panes. Reject duplicate/unknown ids, missing assignments, non-finite geometry, negative sizes/radii and intersecting positive-area rectangles using the existing error channel, without applying a partial layout. A stale revision is ignored and returns current state; it must not reposition a slot reused for another tab. Zero-sized panes create no hole and show no native surface until measurable; they keep their model assignment and protection. A newly assigned slot stays hidden until geometry for its revision is available. Covered panes retain real bounds, but punch no hole. This replaces today's `viewport: null` without losing the last measured size.

The revision advances only when a pane is added or removed (including the first assignment creating an empty window's pane), or the committed split ratio changes. Replacing a tab within an existing pane keeps the revision: geometry is keyed by pane id, so tab replacement cannot make it stale. Advancing on every assignment was rejected because it hid the replacement page until another chrome round trip, despite its pane already having valid geometry.

`set_layout` updates bounds, reconciles slots and rebuilds the mask through the serialized change path in `state.rs`; it must not race a tab switch. Resolve each slot to its current `(window, viewport)` before moving or showing it. Hidden background slots never punch holes. Cut the union of uncovered pane rectangles from the chrome, then add registered overlays back. Divider and pane controls stay in solid chrome. Keep bounds and mask in one layout operation, as [Chrome layering](chrome-layering.md) requires; this does not claim atomic native painting across HWNDs. Re-raise chrome after creation/reparenting as today.

Add async chrome-only intents returning `BrowserState`: `split_tab(tab: TabId)` (clicked hidden tab beside the focused tab), `close_pane(tab: TabId)` (remove the named visible assignment), `set_split_ratio(tab: TabId, ratio: number)` (name either visible tab), and `focus_pane(tab: TabId)` (focus the named visible assignment). `select_tab` keeps its signature and adopts the selection table. Popup, foreign-window, missing-tab, no-split, already-visible split target and invalid-ratio requests fail through the existing error channel without mutation. Repeated `focus_pane` for the focused tab is a no-op. No page receives IPC. Generate bindings from Rust; use `@ipc/commands` and window-targeted event listeners.

## Pool and optimization

Every visible external, non-crashed tab reserves a slot and is protected from eviction, freezing and automatic discarding, regardless of which pane is focused. Internal and crashed tabs reserve none. A restoring cover hides native input, not the tab's visibility or reservation. Focusing the other pane alone emits no `Leave`, capture, blank or freeze for the previous pane; replacing/removing an assignment does. Resume precedes showing or reusing a frozen slot. Preview and draft restoration remain keyed by tab, and preview covers are per pane.

Generalize the existing reservation calculation across all windows:

```text
effective_capacity = max(configured_capacity,
                         max(1, visible_web_count) + fixed_web_count + other_must_run_count)
```

Here `fixed_web_count` includes visible fixed tabs, matching today's conservative counting; `other_must_run_count` excludes fixed and visible tabs. Internal/crashed tabs are excluded from slot counts. Audio, capture and connected-page protections retain [Tab optimization](tab-optimization.md#must-run), including Always-policy exceptions. This preserves current semantics rather than silently removing must-run reservations to match the earlier first-release shorthand.

At configured capacity, reuse a parked slot, grow up to effective capacity, then evict the lowest-loss, least-recently-shown unprotected occupant. Never steal the other pane's slot. If no slot is available, retain `NoSlotAvailable` and discarded presence; keep the requested pane assigned and show an in-pane retry using existing reload, with command failure reported normally. Native creation failures likewise must not blank a healthy pane. Capacity reduction, memory pressure and closing a pane trim only unprotected slots, following existing spare/parking policy. Splitting may therefore exceed Loaded tabs; it is a background-slot setting, not permission to blank visible pages.

## Focus and input

Clicking or tabbing into a content webview updates focused viewport in Rust. Internal-page focus is reported from chrome using the explicit tab id. Raising or showing a sibling surface must not steal focus. Explicit pane selection focuses its content webview, or its chrome-rendered page container when internal/crashed. Moving to the shared toolbar preserves logical pane focus; submitting the address targets that tab. Switching panes cancels an address edit and shows the newly focused tab's URL, following current active-tab behavior.

Native keys still use `AcceleratorKeyPressed` and the Rust keymap, with handled/repeat behavior unchanged. A page shortcut captures its source tab and slot ownership when received, not only its window. Tab-specific actions (close, reload, history, address focus and DevTools) revalidate that ownership and visible assignment before acting, dropping stale requests. Strip-selection shortcuts resolve the window's logical focused pane in queue order instead, so consecutive queued Ctrl+Tabs advance consecutively even when the first replaced their source page. Chrome shortcuts resolve the logical focused pane in queue order. Dispatch tab operations with explicit ids; a delayed F5 from a replaced page must never reload its replacement. Unbound keys remain with the native surface that has focus. An `AddressFocusRequested` still names the tab and waits for its focused assignment to render.

Native focus observation is a prerequisite: current window focus events only update window recency, and keys alone cannot detect clicking another pane. The exact Tauri/WebView2 focus hook and its ordering with accelerator delivery have not been verified; choose and prove an available hook before enabling two panes. Do not rely on content IPC, DOM pointer events through the native hole, or invent a platform API.

## UI

- A hidden tab's context menu offers **Open in split view**, placing it to the right of the focused tab and focusing the new pane. The existing tab stays left. With two panes, or on an already-visible tab, disable it with the reason. A visible split tab's menu offers **Close pane**, which keeps the tab open. Tab Close and Ctrl+W still close the tab itself.
- Splits are created only through **Open in split view**. Click a pane or select its visible tab to focus it; existing Ctrl+Tab and Ctrl+1–9 select tabs and focus their panes under the selection table. No dedicated split shortcuts or drag-to-split in this release; tab dragging still reorders the strip.
- Two side-by-side panes only, initially equal width. A 4 CSS-pixel solid divider separates native holes. A focusable separator names the adjacent pages, exposes orientation and percentage, and supports Left/Right in 5 percentage-point steps, Home/End to limits, Enter to reset equally, Escape to cancel a pointer drag. Pointer capture keeps resize working across native surfaces. Each pane has a persistent chrome **Close pane** button with an accessible name; it is outside the page hole and at least 24 by 24 CSS pixels.
- Ratio range is 0.2–0.8. Clamp pointer/keyboard resizing to at least 240 CSS pixels per pane where available. Below 484 CSS pixels of available content width, keep both panes and use equal widths; disable divider resizing and preserve the preferred ratio for when width returns. Never auto-close a pane or change the window's minimum size. Narrow internal pages scroll within their pane.
- During dragging, update measured rectangles through refs and coalesce layout reports per animation frame; commit the ratio once on release. Cancel restores pre-drag geometry. Replacing a pane or changing layout revision cancels an in-progress drag.
- Reuse Haku's tokens, corner radius and compact chrome controls. Indicate both visible tabs in the strip with a pane-position marker; keep the raised selected-tab treatment only for the focused tab. Give the focused pane's chrome control a visible focus treatment and an accessible current-pane label. Loading, crash and error feedback stays inside its pane; a healthy sibling remains usable. A visible unfocused pane with a pending page dialog shows an accessible **Dialog waiting** marker in its solid chrome edge, outside the page hole; clicking it focuses the pane and presents the dialog.

## Session persistence

Persist the split, assignments, focused pane and committed ratio in each normal window. Continue storing all tabs in strip order as URL/title/fixed records; no slots, native focus, drafts, previews, dialogs or popup connections survive restart.

Additive `SessionWindow` field:

```ts
split?: {
  tabs: [number, number]; // indices into this window's stored tabs, left then right
  focused: 0 | 1;
  ratio: number;
};
// Existing tabs, active and bounds stay; active mirrors the focused tab index.
```

One-pane windows omit `split`. Pane ids are recreated on restore, as tab ids already are. Keep `active` for reading by older binaries that ignore the additive field; such binaries reopen unsplit. No top-level version is needed for this additive change.

Read today's `{ windows: [...] }` format without `split` as one viewport on `active`, with today's first-tab fallback. Preserve the existing older flat `{ tabs, active }` migration to one window. For a split, validate two distinct in-range indices, focus in 0–1 and a finite ratio in 0.2–0.8. Map indices through URL filtering before applying assignments: if either referenced tab is filtered out, or any split field is invalid, drop only the split and restore using existing active-index filtering/fallback. Deserialize the optional split tolerantly before validation: a wrong field type must not make `storage::read_json` reject the entire session and lose its tabs. Never substitute a different page into a stored pane silently. Empty windows and home-page fallback keep current rules.

Build via `Browser::restored` with external tabs discarded and no slot state. Reconcile when each window reports matching geometry; both visible external tabs may then load, without stealing another window's slot. A chrome renderer reload reads the committed split from Rust; engine restart uses the persisted split. Splits do not change what counts as a visit.

## Findings and verification limits

- The APPROVED first-release capacity shorthand omits must-run background reservations present in IMPLEMENTED pool/optimization specs and `Browser::reserved`. D5 settles the arithmetic; update `docs/first-release.md` capacity wording in slice 1, with the implementation, as required for changes to APPROVED/IMPLEMENTED documents. It is not edited in this documentation-only change.
- One-viewport code still predates the approved named-viewport direction, but first-release explicitly defers that refactor to slice 1; this is recorded legacy, not a newly discovered conformance defect.
- Native sibling focus observation, focus ordering, pointer capture across native holes, multi-hole input masking and two-pane rendering have not been runtime-verified. They are implementation acceptance checks, not claims about an available Tauri/WebView2 API. Shared-renderer crash fan-out remains unverified in the existing crash spec too.
- `src/features/context-menu/items.ts:tabMenu` offers **Keep loaded** on a tab, matching IMPLEMENTED [Context menus](context-menus.md#interface-menus), whereas IMPLEMENTED [Webview pool § Fixed tabs](webview-pool.md#fixed-tabs) explicitly says the control is not on the tab itself. A user right-clicking a tab can therefore bypass the site-menu-only interaction that the pool spec describes. This existing documentation conflict is outside this documentation-only scope; no interaction is reversed here.
- This focused inspection is not a full conformance audit. No UI was built or rendered for this spec.
