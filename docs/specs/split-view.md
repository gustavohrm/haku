# Split view

This spec builds on [First release § Viewports, not a viewport](../first-release.md#viewports-not-a-viewport). The [decisions](#decisions) below govern implementation. Rust remains the authority; React renders browser state and reports measured geometry.

## Problem

Before split view, Haku equated the selected tab with the only page visible in each window. Comparing two pages required switching tabs or opening another window. Adding a second content element alone would have left its page hidden, unprotected, incorrectly positioned, or targeted by commands for the other page.

Slices 1–4 implemented named viewports, focus targeting, two-pane policy and pane controls. Maintainer testing exposed a merit problem with that model: the split belonged to the window, so selecting an unrelated tab replaced a pane and leaving split view required dismantling it. The pane header repeated the strip's title and close controls, while the 1/2 markers served testing rather than everyday use. The revised model preserves comparisons as tab pairs and lets ordinary tab selection leave them intact. The rejected choices and the evidence reversing them are recorded under Decisions.

## Model

A split is an ordered pair of distinct tabs in one normal window, left then right, with its own committed ratio. A window may hold several disjoint pairs; a tab belongs to at most one. Each pair's tabs are adjacent in strip order. Popups retain one viewport and cannot hold pairs. D3 limits the on-screen layout to two side-by-side viewports, not the number of background pairs.

The selected tab determines the on-screen layout: an unpaired tab fills one viewport; either member of a pair shows both members at that pair's ratio, with the selected half focused. Only those assignments are **visible tabs**, including internal and crashed pages. Background pairs are relationships, not hidden viewports. Rust owns pairs and projects them into the current `viewports` and `focusedViewport`. Pane ids are stable for the lifetime of an on-screen pane, are window-local, and are not session state. Removing a pane does not renumber the survivor.

The **focused viewport** is the last pane chosen for browser actions, even while chrome has native focus; its assignment is the **focused tab**. `active` remains the derived compatibility projection of that tab. Native webview focus and window focus are separate facts. Losing window focus clears neither pair membership nor logical focus. The toolbar, address field and selected-tab treatment follow `active`.

| Action                                                                              | Result                                                                                                                                                                                           |
| ----------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Select an unpaired tab                                                              | Show it alone, full width. Retain every pair in the background.                                                                                                                                  |
| Select either member of a pair                                                      | Show that pair at its ratio; focus the selected half without swapping its left/right order.                                                                                                      |
| Click the other on-screen half                                                      | Move focus only; retain assignments, ratio and revision.                                                                                                                                         |
| Ctrl+Tab or Ctrl+1–9                                                                | Traverse individual tabs in strip order and apply the same selection rules.                                                                                                                      |
| Open a foreground tab from chrome or a page, or reopen a closed tab                 | Open a normal unpaired tab and show it alone. Preserve existing pairs, opener connections and destination-window rules. Reopen restores the tab, not its former pair.                            |
| Open a background tab                                                               | Keep selection and on-screen assignments. Retain existing background/opening policy, subject to pair adjacency below.                                                                            |
| Open a page-requested popup window                                                  | Keep existing popup-window and opener behavior; never add it to a pair.                                                                                                                          |
| Open in split view on another unpaired tab                                          | Pair it with the selected unpaired tab, move the partner immediately to the selected tab's right, show the pair at 0.5 and focus the partner.                                                    |
| Open in split view when either tab is already paired, or on the selected tab itself | Disable with an accessible reason. Do not replace a partner or dissolve a pair implicitly (D8).                                                                                                  |
| Close either tab of a pair                                                          | Dissolve the pair and close that tab. If on screen, show the survivor alone and focus it, even when the other half was focused. If in the background, keep current selection and layout.         |
| Separate tabs on either member                                                      | Dissolve the pair without closing tabs or reordering. If on screen, show the currently focused member alone; if in the background, keep current selection and layout.                            |
| Close an unpaired selected tab                                                      | Prefer its same-window opener, then the nearest tab to its right, then its left, under existing close rules. Apply selection rules to the replacement, including showing its pair if it has one. |
| Close an unpaired background tab                                                    | Keep selection and layout.                                                                                                                                                                       |
| Drag either member                                                                  | Move the entire pair as one unit, preserving left/right order. Drop targets exist only between units, never between pair members.                                                                |

Closing the last normal-window tab retains the existing home-page replacement; closing a popup's tab closes its window. Bulk close operations apply the same rules sequentially. Closing or separating a pair does not retain an undoable layout record; reopen restores only the closed tab.

All insertion and reorder paths preserve adjacency, including background link opens and reopen. When an existing insertion position falls between two paired tabs, place the inserted tab immediately after the pair instead. This is the smallest adjustment to existing insertion rules; background opens otherwise remain unchanged. `reorder_tab` retains its signature but resolves either member to its pair and normalizes a destination inside another pair to after that pair. Chrome shows only legal gaps.

## Layout and IPC

Rust owns pairs and their ratios, pane ids, current assignments and focused id. React owns measurement and temporary divider-drag geometry. Ratio is the first pane's share of the available width after the divider; orientation is side by side only. Geometry is never session state.

Revised split-related fields in each window's `BrowserState` (other existing fields remain):

```ts
type SplitViewState = {
  viewports: { id: string; tab: TabId }[]; // currently on screen only
  focusedViewport: string;
  splits: { tabs: [TabId, TabId]; ratio: number }[]; // all pairs, left then right
  layoutRevision: number; // on-screen pane set or shown committed ratio changed
};
// Remove splitRatio: derive the shown ratio from the pair containing active.
// active remains derived from focusedViewport.
```

Replacement for `Layout`, still passed as the `layout` argument of async `set_layout`:

```ts
type Layout = {
  revision: number; // BrowserState.layoutRevision being rendered
  viewports: {
    id: string;
    rect: Viewport; // existing x, y, width, height, in chrome CSS pixels
    covered: boolean; // internal page, crash notice or restoring preview
    radius: number; // measured from this pane's CSS
  }[];
  overlays: Overlay[]; // existing window-relative rectangles and radii
};
```

Every assigned pane is reported, including covered panes. Reject duplicate/unknown ids, missing assignments, non-finite geometry, negative sizes/radii and intersecting positive-area rectangles using the existing error channel, without applying a partial layout. A stale revision is ignored and returns current state; it must not reposition a slot reused for another tab. Zero-sized panes create no hole and show no native surface until measurable; they keep their model assignment and protection. A newly assigned slot stays hidden until geometry for its revision is available. Covered panes retain real bounds, but punch no hole. Keep the existing covered-pane protocol without losing the last measured size.

The revision advances when the set of on-screen viewport ids changes (including initial assignment, single-to-pair, pair-to-single and switching to another pair), or the shown pair's committed ratio changes. Reuse the one-pane geometry for ordinary single-tab selection; focus-only changes within the same pair and edits to background pair metadata do not advance it. When switching pairs, replace the pane set so old pair geometry cannot be accepted even if both pairs have equal ratios. Tab ids are not geometry: ordinary replacement within a retained single pane does not invalidate its bounds. Advance only for geometry identity or committed sizing changes, avoiding the previous needless blanking on every tab assignment.

`set_layout` updates bounds, reconciles slots and rebuilds the mask through the serialized change path in `state.rs`; it must not race a tab switch. Resolve each slot to its current `(window, viewport)` before moving or showing it. Hidden background slots never punch holes. Cut the union of uncovered pane rectangles from the chrome, then add registered overlays back. The divider and focus outline stay in solid chrome. Keep bounds and mask in one layout operation, as [Chrome layering](chrome-layering.md) requires; this does not claim atomic native painting across HWNDs. Re-raise chrome after creation/reparenting as today.

Async chrome-only intents return `BrowserState` (D2):

| Command                                      | Meaning                                                                                                                                                              |
| -------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `split_tab(tab: TabId)`                      | Create a pair from the selected unpaired tab and the named distinct unpaired partner; move the partner right, use ratio 0.5 and focus it.                            |
| `separate_tabs(tab: TabId)`                  | Dissolve the named tab's pair, including a background pair. Retain both tabs. Replace `close_pane`; do not retain an alias with changed meaning.                     |
| `set_split_ratio(tab: TabId, ratio: number)` | Commit the ratio of the pair containing the named member, including a background pair. Advance layout revision only if that pair is on screen and its ratio changed. |
| `focus_pane(tab: TabId)`                     | Focus the named currently visible assignment; it does not reveal a background pair. Repeating it for the focused tab is a no-op.                                     |

`select_tab` keeps its signature and adopts the model table. Keep the existing `reorder_tab` command with pair-unit semantics; no generic pair setter, pair-id command, new event or page IPC is needed. A pair is identified by either member; no durable split id is required. Reject missing or foreign-window tabs, popup requests, self-pairing, already-paired creation operands, separation/ratio for an unpaired tab, focus of a hidden tab, and non-finite or out-of-range ratios through the existing error channel without mutation. Revalidate eligibility in Rust, including when a menu became stale. Generate bindings from Rust; use `@ipc/commands` and window-targeted event listeners.

## Pool and optimization

Only the single tab or pair on screen counts as visible. Background pairs follow ordinary background policy, including fixed/audio/capture/opener protection; pair membership alone grants no reservation or protection. Every visible external, non-crashed tab reserves a slot and is protected from eviction, freezing and automatic discarding, regardless of which pane is focused. Internal and crashed tabs reserve none. A restoring cover hides native input, not the tab's visibility or reservation. Focusing the other pane alone emits no `Leave`, capture, blank or freeze for the previous pane; hiding a single tab or pair does for each tab leaving visibility. Returning to a pair resumes or restores either member as ordinary policy requires. Resume precedes showing or reusing a frozen slot. Preview and draft restoration remain keyed by tab, and preview covers are per pane.

Generalize the existing reservation calculation across all windows:

```text
effective_capacity = max(configured_capacity,
                         max(1, visible_web_count) + fixed_web_count + other_must_run_count)
```

Here `fixed_web_count` includes visible fixed tabs, matching today's conservative counting; `other_must_run_count` excludes fixed and visible tabs. Internal/crashed tabs are excluded from slot counts. Audio, capture and connected-page protections retain [Tab optimization](tab-optimization.md#must-run), including Always-policy exceptions. This preserves current semantics rather than silently removing must-run reservations to match the earlier first-release shorthand.

At configured capacity, reuse a parked slot, grow up to effective capacity, then evict the lowest-loss, least-recently-shown unprotected occupant. Never steal the other pane's slot. If no slot is available, retain `NoSlotAvailable` and discarded presence; keep the requested pane assigned and show an in-pane retry using existing reload, with command failure reported normally. Native creation failures likewise must not blank a healthy pane. Capacity reduction, memory pressure and separating a shown pair trim only unprotected slots, following existing spare/parking policy. Splitting may therefore exceed Loaded tabs; it is a background-slot setting, not permission to blank visible pages.

## Focus and input

Clicking or tabbing into a content webview updates focused viewport in Rust. Internal-page focus is reported from chrome using the explicit tab id. Raising or showing a sibling surface must not steal focus. Explicit pane selection focuses its content webview, or its chrome-rendered page container when internal/crashed. Moving to the shared toolbar preserves logical pane focus; submitting the address targets that tab. Switching panes cancels an address edit and shows the newly focused tab's URL, following current active-tab behavior.

Native keys still use `AcceleratorKeyPressed` and the Rust keymap, with handled/repeat behavior unchanged. A page shortcut captures its source tab and slot ownership when received, not only its window. Tab-specific actions (close, reload, history, address focus and DevTools) revalidate that ownership and visible assignment before acting, dropping stale requests. Strip-selection shortcuts resolve the window's logical focused pane in queue order instead, so consecutive queued Ctrl+Tabs advance consecutively even when the first replaced their source page. Chrome shortcuts resolve the logical focused pane in queue order. Dispatch tab operations with explicit ids; a delayed F5 from a replaced page must never reload its replacement. Unbound keys remain with the native surface that has focus. An `AddressFocusRequested` still names the tab and waits for its focused assignment to render.

Native sibling focus observation was introduced in slice 2; retain it and explicit tab ownership. Switching from a pair to a single tab, or to another pair, invalidates pending native-focus work for assignments that left visibility. Do not rely on content IPC or DOM pointer events through native holes. Slice 4b must recheck focus ordering in the running app; this documentation change does not claim runtime verification.

## UI

- An unpaired tab's context menu offers **Open in split view**. It pairs with the selected unpaired tab only when they are distinct. Disable it with a visible, accessible reason for the selected tab itself, an already-paired target, or an already-paired selection (recommended reason: **Separate the selected pair first**). Either member of any pair offers **Separate tabs**, including background pairs, replacing **Close pane**. Tab Close, middle click and Ctrl+W still close the individual tab.
- Draw each adjacent pair as one joined strip item, with shared outer shape, no gap between its two halves and the normal gap between it and neighboring items. Each half keeps its own title, favicon, close button, context menu and selection target. Only the focused tab has selected-tab treatment; the join identifies pairs even in the background. Retain normal keyboard access to each tab and its menu, and expose pair membership and left/right position accessibly without visible numbers. Remove 1/2 strip numbers in every build. Drag either half as a unit; no drag-to-split or dedicated split shortcuts (D6).
- No per-pane header, repeated title or Close pane button. While a pair is on screen, draw a thin accent outline around the focused pane, in solid chrome outside its native hole so it stays visible and does not intercept page input. Retain an accessible current-pane label and ordinary keyboard focus indicators. Single-tab view has no split-focus outline. Reuse Haku's theme tokens, radius and density, with sufficient non-text contrast in both themes.
- A **Dialog waiting** strip badge belongs to the waiting tab, has an accessible name identifying that tab and can be activated by keyboard. Selecting that tab or activating its badge follows normal selection, focuses its pane and presents its dialog. Use existing per-tab dialog state; dialogs remain window-modal, focused-tab only. Loading, preview and crash feedback remain per pane.
- D4 is unchanged: two side-by-side panes, ratio default 0.5 and range 0.2–0.8, a 4 CSS-pixel solid divider, and at least 240 CSS pixels per pane where possible. Below 484 CSS pixels of content width, render equal widths and disable resizing while preserving the preferred ratio. Never collapse automatically or change the window minimum size. Narrow internal pages scroll within their pane.
- The focusable separator names adjacent pages, exposes orientation and percentage, and supports Left/Right in 5 percentage-point steps, Home/End to limits, Enter to reset equally and Escape to cancel pointer drag. Pointer capture keeps dragging across native holes. Temporary geometry uses refs and animation-frame-coalesced layout reports; commit once on release, restore the pre-drag ratio on cancel. Pair replacement, separation or changed layout revision cancels a drag.
- Container resize alone must not cancel an active drag: retain capture and provisional ratio, remeasure and clamp it to current rendered limits, then continue. In a too-narrow container, render equal widths; preserve the pre-drag preferred ratio for cancellation. Defer observer-triggered state/style writes to a coalesced animation frame, skip unchanged values and cancel scheduled work on cleanup. This removes the observer feedback warning without suppressing it and avoids writing layout-affecting styles inside the observer callback.

## Session persistence

Persist every pair and its committed ratio per normal window, including background pairs. Store tabs in strip order as URL/title/fixed records, plus existing `active` and bounds. `active` identifies the selected tab: restore its pair if it belongs to one, otherwise show it alone. No separate stored focus or shown-pair field is needed. Slots, native focus, drafts, previews, dialogs, geometry and popup connections do not survive restart.

Additive `SessionWindow` field (D9):

```ts
splits?: {
  tabs: [number, number]; // indices into this window's stored tabs, left then right
  ratio: number;
}[];
// Existing tabs, active and bounds stay. Omit splits when no pairs exist.
```

Fresh tab and pane ids are assigned on restore. Older binaries ignore the additive field and reopen on `active` unsplit; no top-level version is needed. Retain both existing readers: `{ windows: [...] }` without `splits` and the older flat `{ tabs, active }` migration. Inspection of `tauri/src/storage/session.rs` at `1476b91` confirms there is no `split` field or writer; slice 5 was never built. No earlier single-`split` reader is required for this branch, and unknown `split` data is ignored as before. If evidence of a shipped writer appears before implementation, revise D9 to specify its migration rather than inventing one here.

Deserialize the optional list and each entry tolerantly: a wrong list type acts as no pairs; a malformed entry drops only that pair, never the entire session or other valid pairs. Validate distinct in-range integer indices, stored left/right adjacency, no member reused by another accepted pair, and a finite ratio in 0.2–0.8. Accept entries in stored order; the first valid pair claims its members and a later overlapping entry is dropped. Map indices through URL filtering before assignments: if either member is filtered out, drop only that pair; never substitute another tab. Retain existing active-index filtering/fallback independently, so an invalid pair does not discard the selected tab. Empty-window and home-page fallback rules remain unchanged.

Build through `Browser::restored`, with external tabs discarded and no slot state. Reconcile only the selected single tab or pair when each window reports matching geometry; background pairs do not eagerly load. A chrome renderer reload reads all committed pairs from Rust; engine restart uses persisted pairs. Splits do not change what counts as a visit.

## Implementation slices

Slices 1–4 were built through `1476b91`: named viewport refactor, native focus targeting, two-pane policy/IPC, then pane rendering and controls. Slice 4b replaces that window-owned model with persistent in-memory pairs and revised chrome. Session persistence remains slice 5, so this spec stays APPROVED. Deterministic policy and geometry tests run in Rust modules or sibling test files, with colocated Vitest for interface behavior. Native Windows acceptance remains manual; automated checks do not prove native focus, input masking, rendered contrast or the absence of observer warnings in WebView2. Regenerate bindings for boundary changes and run `pnpm verify` before delivering each slice.

### Slice 4b: persistent tab pairs and revised chrome

In `tauri/src/browser.rs`, `browser_tests.rs`, `ipc/{commands,mod}.rs` and state export, separate pair membership/ratios from visible assignments. Implement the model table, pair-unit insertion/reorder, revised commands and geometry revision rules. Update `src/features/{tabs,viewport,context-menu,feedback}`, styles and i18n for joined pairs and drag, menu eligibility/separation, header removal, focused-pane outline, dialog badges and removal of all 1/2 numbers. ## Findings and verification limits

The following implementation-impact findings describe the inspected `1476b91` baseline that motivated the revision. Slice 4b addresses the model, IPC, adjacency, chrome and divider findings in code; the native acceptance checklist above remains to be run. Chrome uses pointer capture and a drag threshold for joined units, computing legal gaps from strip geometry and cancelling on Escape or order/membership changes. Its native drop handler stays enabled: disabling it for HTML drag/drop did not weigh losing wry's `AllowExternalDrop(false)` on the IPC-holding chrome webview, violating the [security boundary](../guidelines/security.md). Verify that external file, link and text drops cannot navigate chrome, including internal pages. Content webviews retain their existing handler settings.

- **Merit, now revised:** `Window::assign` replaces the focused assignment and `Window::split_ratio` belongs to the window. After pairing A/B, selecting C replaces one member; the maintainer cannot view C alone and later return to A/B intact. D2/D8 replace this model with independent membership and visible projection. This is a reversal of the old decision, not a defect in code that followed it.
- **Implementation impact:** `split_tab`, `close_pane` and `set_split_ratio` currently validate visibility and a one/two-pane window; background pairing metadata requires different validation and `separate_tabs`. `Window::remove_pane` clears the window ratio; pair dissolution must preserve unrelated ratios. `RestoredWindow` carries only tabs/active, so slice 5 must extend restoration without calling live open/select paths.
- **Implementation impact:** `Browser::reorder_tab` moves one tab and page opens insert after their opener. Both can separate pair members; adjacency must be enforced in Rust, not just by a joined strip wrapper. The present `TabStrip` maps independent `TabItem`s and has no pair-unit drag interaction, so slice 4b includes that interaction rather than just changing its appearance.
- **Implementation impact:** `ViewportPanes` reads `splitRatio`, keys page containers by pane id and passes assignment/revision changes to the divider. Pair switching must invalidate stale geometry/focus while ensuring internal-route state and preview covers do not transfer from one tab to another. Retain per-tab ownership and the existing source-bound toolbar-popup closure; hiding a pair is now a common transition.
- **Known UI defects, slice 4b:** `split-divider.tsx`'s `ResizeObserver` callback currently calls `setWidth`, writes `--split-ratio` and ARIA state, and clears drag/capture on every observation. During container resize this cancels a live drag; layout-affecting observer writes are implicated in the reported `ResizeObserver loop completed with undelivered notifications` warning. Coalesce writes outside observer delivery and verify the native warning is gone, rather than suppressing it. This change records the fixes; it does not implement them.
- **Built versus intended:** slices 1–4 remain the legacy window-owned implementation until slice 4b. The architecture's implemented viewport projection remains useful, but is not the new pair store. No code was changed or native focus, pointer capture, multi-hole masking, popup ownership, contrast or rendered UI reverified for this documentation revision. Retain these runtime checks in implementation acceptance; shared-renderer crash fan-out is still not promised.
- Session inspection confirms tabs/active/bounds only; persistence is still slice 5. Pair metadata must not eagerly realize background pages or change fixed/must-run policy. The first-release capacity wording was already updated in slice 1; D5 does not change that formula.
- The existing Keep loaded conflict remains outside this revision: `context-menus.md` and `tabMenu` permit the tab action while `webview-pool.md` says it belongs only in the site menu. No fixed-tab interaction is reversed here. This focused inspection is not a full conformance audit.
